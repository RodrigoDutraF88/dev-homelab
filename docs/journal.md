Multi-Container Orchestration: Docker Compose allows you to define dozens of different containers like traefik, postgresql, redis etc.Because they all share the same docker-compose.yml, they can easily share networks.

Container-to-Container: Containers on the same docker network can talk to each other directly using their service names.

Container-to-Host: The ports: mapping like 80:80, is for exposing a port from inside the container out to your actual physical machine so that me or external traffic can reach it from a browser.

Traefik:Traefik is an automated reverse proxy and load balancer that plugs directly into Docker to dynamically route web traffic to your containers using clean subdomains and automatic SSL certificates, eliminating the need for manual routing or port numbers.

reverse proxy: Is a intermediate server that sits in front of web servers, intercepting all requests before they reach the origin server.

Debian and Alpine: are two Linux distributions commonly used as base images for Docker containers. Debian is a complete, stable, and highly compatible distribution with a large software ecosystem, while Alpine is a lightweight and minimal distribution designed to produce very small container images.

Redis (Remote Dictionary Server) is an open-source, in-memory data structure store used primarily as a database, cache, message broker, and streaming engine. Unlike traditional databases that store data on hard drives or SSDs (disk-based storage), Redis keeps its entire dataset in RAM, allowing for exceptionally fast read and write speeds (sub-millisecond latency). While it operates in-memory, it can also persist data to disk through snapshots or append-only logs (AOF) to ensure durability.

Secrets in version control: .gitignore only stops files that git is not already tracking. My .env was committed in the very first commit, so adding it to .gitignore later did nothing at all: git kept tracking it because it was already in the index. The fix is `git rm --cached .env`, which removes the file from git's index while leaving it on disk. From that point on the gitignore rule finally applies.

Untracking is only half the job though. Every old commit still contains the file, so anyone who clones the repo can read the secrets out of the history. That means the secrets have to be treated as burned and rotated, i.e. replaced with new values, not just hidden.

Rotating a database password is not the same as editing .env. POSTGRES_PASSWORD is only read once, the very first time the container initialises an empty data directory. After that the password lives inside the postgres volume, so changing the variable and restarting does nothing. The real rotation is an SQL statement against the running database (ALTER USER ... WITH PASSWORD ...), and .env is updated to match. Redis is the opposite: its password comes from the --requirepass command flag, which is re-read on every start, so there a restart is genuinely enough. Same for Traefik's basic-auth hash, which is just a label.

Compose reads .env values through variable interpolation, so a literal dollar sign has to be written as $$. This matters for the bcrypt hash from htpasswd, which is full of them ($2y$05$...). Written with single dollars, Compose treats $2y and $05 as variable references, substitutes them with empty strings, and stores a truncated hash, which silently locks you out of the dashboard rather than throwing an error.

A rotation is only real if the old credential actually stops working. Worth testing both directions: the new password succeeds and the old one is refused. Testing only the new one would not have caught a postgres password that was never really changed.

Rewriting history: untracking a file only cleans the latest commit. To remove it from every commit, the history itself has to be rebuilt, with `git filter-repo --path .env --invert-paths`. This walks all 13 commits, rewrites each one without that file, and repacks the repository. Because a commit's identity is a hash of its content, removing a file changes every commit ID from the first affected commit onward. The old and new histories share no commits at all, which is why the remote will not accept a normal push and needs `--force`.

Two side effects worth knowing about. The commit whose only change was deleting `.env` became an empty commit once `.env` no longer existed anywhere, so filter-repo dropped it: 13 commits became 12. And filter-repo rebuilds the working directory from the new history, which deleted my on-disk `.env` even though it was untracked and gitignored. It holds the live passwords for the running stack, so losing it would have meant regenerating everything. Taking a full copy of the folder before running a destructive command is what made that a non-event rather than an outage.

Force pushing is not a complete fix, only a cleanup of the public record. Anyone who cloned or forked the repo before the rewrite still has the old commits on their machine, and GitHub may keep the old objects reachable for a while. Rotating the passwords is the part that actually protects the stack. The rewrite just stops the old values being handed to the next person who clones. But since my project was private, it's safe to say that nothing leaked.

uptime-kuma: Uptime Kuma is a self hosting monitoring tool
What are the differences between traefik, pontainer and uptime kuma? Traefik gets traffic to your services, Portainer lets you manage the containers behind those services, Uptime Kuma watches whether those services are actually responding.

Prometheus & Grafana: 
Prometheus: is a metrics collection, time-series database, and alerting system.It features a query language called PromQL (Prometheus Query Language) that allows developers to filter, aggregate, and compute rates of change across metrics. 
Grafana: is a data visualization, dashboarding and exploration platform. Grafana queries backends like Prometheus and renders the data into costumized graphs, heatmaps, gauges, status maps, and tables.
How they work together: My server exposes a route, prometheus scrapes that route, stores the time-series points, and monitors for alert conditions. Grafana connects to prometheus, runs PromQL queries in the background and displays real-time health graphs on a dashboard.

Http vs Https: HTTP sends every request and response as clear text, so anyone sitting between the browser and the server (the wifi you are on, any router along the way) can read it and even change it. HTTPS is the same HTTP, only wrapped in a TLS layer that encrypts the traffic and proves the server really is the one it claims to be. Everything in this homelab was plain HTTP until roadmap step 8, which meant the Traefik dashboard password and the Grafana login were travelling in the open. On a laptop talking to itself that is not dramatic, but it stops being acceptable the moment the stack is reachable from anywhere else.

Certificate Authority: encrypting is not enough on its own, because you could be encrypting your traffic straight into the hands of an impostor. A certificate authority is a third party that both sides already trust: it checks that whoever asks for a certificate actually controls the domain, and then signs that certificate with its own key. Browsers and operating systems ship with a built-in list of CAs they trust, so anything signed by one of them is accepted without a word. The certificate I generated with openssl for *.localhost is signed by nothing but itself, the issuer and the subject are the same line, and that is exactly why the browser complains: the encryption is real, but nobody is vouching for who I am. It is also why no CA could help here even if I asked, since localhost is a name that belongs to everybody and control of it cannot be proven.

TLS: TLS (Transport Layer Security, the successor of SSL) is the layer that turns HTTP into HTTPS. At the start of a connection the client and the server do a handshake: the server presents its certificate, the client checks who signed it and whether the name matches the site it asked for, and the two agree on a session key that encrypts the rest of the conversation. In this stack Traefik is where TLS is terminated, meaning the browser speaks HTTPS to Traefik and Traefik speaks ordinary HTTP to the containers behind it over the dev-homelab network. That second hop never leaves the machine, so it is fine, and it means no individual service has to know anything about certificates. One thing that caught me out: a router marked tls=true only answers TLS connections, so leaving it listening on port 80 as well achieves nothing, plain requests simply stop matching and come back as 404. The fix is to redirect at the entrypoint instead, so :80 answers everything with a 301 to :443.

Let's Encrypt: a free, automated certificate authority. Instead of buying a certificate and installing it by hand, the server proves it controls the domain over a protocol called ACME and gets a certificate back in seconds, valid for 90 days and renewed automatically. The proof is a challenge: with HTTP-01 the CA connects back to the domain on port 80 and looks for a file only the real owner could have put there, and with DNS-01 you publish a TXT record in the zone instead, which still works when nothing is reachable from outside and is the only way to get a wildcard certificate. Both need a real registered domain, so none of it works on localhost, which is why the ACME configuration sits in compose/production.yml waiting for the day I have one. Traefik keeps whatever it is issued in an acme.json inside its own volume and handles the renewals on its own. Worth aiming at the staging server first, because the real one allows only 5 failed validations per hour and 50 certificates per domain per week, and those are easy to burn through while a config is still wrong.

DNS-01 vs HTTP1:
HTTP-01: verifies domain ownership by serving a temporary token over public HTTP (port 80), making it simple for standard web servers but limited to individual hostnames. In contrast, DNS-01:verifies ownership by creating a public DNS TXT record, which requires DNS API access and slightly longer propagation times, but enables wildcard certificates (*.domain.com) and allows certificate issuance for private or offline servers without exposing inbound firewall ports.

Container registries and release tags: the Bookshelf app builds in its own repository's CI, but building an image and publishing one are separate things. Every push builds the image and smoke-tests it with `push: false`, which proves it works and then throws it away. Publishing is gated behind a git tag matching `v*`, so the pipeline only pushes to GHCR (GitHub's container registry, ghcr.io) when I deliberately mark a release. I had assumed the workflow was broken because no package ever appeared, but the workflow was fine: I had simply never created the tag. Nothing had ever matched the trigger.

The tag has to be real semver. The workflow derives the image tags from the git tag with docker/metadata-action, which parses it as semver, so `v1.0` is not enough and `v1.0.0` is what produces the `1.0.0` and `1.0` image tags. There is deliberately no `latest`: a moving tag makes "which build is actually running?" unanswerable, and this repo pins every image to an explicit version. Packages on GHCR are also created private even when the repository is public, so the first publish needs its visibility flipped by hand before the homelab can pull it anonymously.

Database migrations: the app's schema is not created by the app. Prisma keeps an ordered folder of migration files, each one SQL that moves the schema forward a step, plus a `_prisma_migrations` table inside the database recording which ones have already been applied. `prisma migrate deploy` compares the two and applies only what is missing, so running it against an already-migrated database is a no-op rather than an error. That is what makes it safe to run on every startup.

Where to run it is the interesting part. Putting it in the app's own startup would mean every replica racing to migrate the same database. Instead it is its own one-shot container: same image (the migration files ship inside it), a replaced entrypoint, `restart: "no"`, and it exits when it is done. The app then declares `depends_on: bookshelf-migrate: condition: service_completed_successfully`, which holds it back until the migration container has exited zero. This is also the first thing in this stack that actually uses the Postgres healthcheck instead of merely declaring one: the migrate container waits on `condition: service_healthy`, because "the container is running" and "Postgres is accepting connections" are not the same moment. So the chain is postgres healthy, then migrate, then app.

Sharing a database server is not sharing a database. The app does not get the homelab Postgres superuser: it gets its own role and its own database inside the same instance, so a mistake in the app cannot reach anything else stored there. This is the payoff for building the shared data services back at step 3 rather than letting the app ship its own Postgres, which is what its local development compose file does.

Build-time versus runtime environment variables: in Next.js, anything named `NEXT_PUBLIC_*` is meant for the browser, which means its value is baked into the JavaScript bundle when the image is built. Setting it in compose at run time therefore only reaches server-side code, and cannot retroactively put it in a bundle that was compiled without it. Ordinary server-side variables are the opposite and are read from the process environment on every start, which is why the database URL and the OAuth secrets can live in `.env` and be swapped without rebuilding anything.

Failing fast on configuration: the app validates its environment at startup with a schema, and refuses to serve if a required variable is missing rather than starting and breaking later at the first login attempt. Mine came up returning 500 on every request because the Discord OAuth credentials were still empty placeholders. That is the validation working as designed, and it is a much better failure than a server that looks healthy until someone tries to sign in. Worth knowing that an empty string counts as missing here, since the schema treats empty as undefined.

Black-box versus white-box monitoring: everything scraped so far reports on itself from the inside. node-exporter reads the host's counters, cAdvisor reads the container runtime's, Traefik publishes its own. That is white-box monitoring, and it needs the thing being watched to cooperate by exposing metrics. The Bookshelf app does not: it is an ordinary Next.js application with no /metrics endpoint, so pointing a scrape job at it would have fetched HTML and left the target permanently down. Black-box monitoring is the other approach, standing outside and checking whether the service actually answers, which needs no cooperation at all. Worth noting the container-level view was never missing: cAdvisor watches every container on the machine, so the app's CPU and memory arrived automatically the moment it started. What was missing was whether it serves.

blackbox-exporter works differently from every other exporter here. It has no targets of its own and no configuration listing what to watch. Prometheus scrapes it and passes the URL to check as a query parameter, the exporter performs that single request, and returns the outcome as metrics: whether it succeeded, how long it took, what status code came back, when the TLS certificate expires. So adding a service to probe is an edit to prometheus.yml, not to the exporter.

Relabeling is what makes that possible, and it is the first genuinely confusing thing in a Prometheus config. The targets listed in the blackbox job are not addresses Prometheus connects to. Three rules rewrite the scrape before it happens: copy the target URL into the target query parameter, keep that URL as the instance label so graphs are named after the service rather than the exporter, and then overwrite the address actually dialled with the exporter itself. Miss the last rule and Prometheus tries to scrape the app directly, which is exactly the failure the exporter existed to avoid.

Probing from two angles is worth more than probing once. The internal URL goes straight to the container, so a failure there means the app itself is broken. The public URL travels through DNS, the reverse proxy and TLS, so a failure there while the internal probe still passes means the app is healthy and the path to it is not. Those are different outages with different fixes, and one probe cannot tell them apart. The public probe also reports certificate expiry as a side effect, which turns "the wildcard renews itself automatically" from an assumption into something measurable, currently reading 87 days out.

A note on where configuration can and cannot come from. The public hostname is written out in full in prometheus.yml rather than as a variable, because Compose interpolates variables into the compose file and never into a file it bind-mounts. The same constraint already forced the ACME email to be hardcoded in traefik.prod.yml. It is easy to assume .env reaches everywhere; it reaches only what Compose itself parses.

Uptime Kuma remains the exception to the whole "nothing is clicked into existence" rule, alongside the Grafana dashboards. Its monitors live in a sqlite file inside its volume and are created through the web UI, with no file-based provisioning to point at. So a monitor added there is real but invisible to the repository, and would not survive rebuilding the machine from scratch. Blackbox probes are the file-defined version of the same signal, which is why they are the better answer here even though both now exist.

Backing up a shared database server: a Postgres instance and a database are not the same thing, and a backup script has to be told which it is protecting. Mine dumped a single database, the one named in POSTGRES_DB, which was correct for exactly as long as the instance held exactly one. The moment the Bookshelf app got its own database alongside it, every book, review and user account was outside the backup, and nothing announced that. The dump kept succeeding, the file kept appearing, the verification kept passing — it was simply dumping something else. A backup that silently protects less than you think is worse than none, because it buys confidence it has not earned.

The fix is to stop hardcoding the list and ask the server for it: query pg_database, skip templates and anything that cannot be connected to, and dump each one to its own file. Now a future app's database is protected the day it is created rather than the day someone remembers to edit the script. That felt like the real lesson — the bug was not the missing database, it was that the script encoded an assumption about the world that quietly expired.

Restoring has a matching trap. My restore script took a file path but always restored into POSTGRES_DB, which was harmless while only one database existed and actively dangerous afterwards: handing it a bookshelf dump would have unpacked the app's tables into the homelab database. It now reads the target out of the filename the backup script writes, refuses to guess when the name does not match that shape, and checks the database exists before asking for confirmation.

Ownership is the part I would not have predicted. pg_restore has a --no-owner flag that reassigns every restored object to whoever is running the restore, which sounds like a convenience and is, right up until the restoring user is not the application's user. Restoring the app's database as the superuser produced a complete, correct-looking set of tables that the app itself could not read: "permission denied for table Book" against its own data. The tables were all owned by the wrong role. Dropping the flag preserves the ownership recorded in the dump, and the cost is that the roles have to exist before the restore — which is exactly what the separate globals file is for. Roles live outside any database, so they were never in the dump to begin with.

None of that was visible from reading the scripts. It came out of actually restoring into a scratch database and then connecting as the application's role to see whether it could read anything. A backup is a claim about the future, and the only way to check the claim is to perform the restore and use the result. Verifying the archive parses is necessary and nowhere near sufficient.

TLS and the Host header: an uptime monitor kept reporting a self-signed certificate for a service whose certificate was demonstrably a valid one from Let's Encrypt. The cause was a stale custom Host header left on the monitor from when it was copied from another one. Setting that header does not only change the HTTP request: Node derives the TLS server name from it, so the connection asked for a certificate belonging to a completely different hostname. Traefik had no certificate for that name and fell back to its default, which is the self-signed one generated for local development, and the client correctly refused it. Two things worth keeping from that. A reverse proxy chooses its certificate from the name the client asks for during the handshake, before any HTTP is exchanged, so a wrong name gets a wrong certificate rather than an error. And "self-signed certificate" was an accurate message the whole time — it just described a request I did not realise I was making.
